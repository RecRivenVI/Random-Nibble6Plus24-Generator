# 26.3 NeoForge 三维度原生前沿基线

调查日期：2026-10-17。三个维度分别完成一次独立 Vanilla/B 8/8 对照，六个 fresh world/JVM 正常结束。只建立当前性能基线，不作为三组配对优化保留、首次玩家出生或客户端渲染验收。

## 问题

原生运行期与保存重载通过，不能说明 B 已接近 Vanilla 生成速度。必须测量真实物理请求的排队、生成、依赖就绪和发送就绪，而不是只比较一个 canonical 调用。

## 方法

当前输入指纹为 `B9EDFD499766306E5B7C3CBCFFE070825E06F50365429E02EC25C2C3890E2D08`。每组四逻辑 CPU、BelowNormal、单游戏 JVM，视距/模拟距离 8/8，master seed 123456789、初始 Chunk (125,-37)。60 秒内第 15/30 秒各沿 X 移动两 Chunk；每维度顺序运行 Vanilla 与 B，测量期间不运行本项目的正确性队列或其它 benchmark。

使用原生玩家距离票据接口，不登录玩家、不操作 GUI。JFR 与原始事件保存于[固定结果目录](../../validations/performance-worldgen/result/b_milestone/26.3-neoforge/)，完整归并入口为 vanilla-comparison.json。工具检查同源、同资源、同轨迹、六个独立 PID/world identity、相同原生请求集合及正常结束；普通 Vanilla 不得进入 Mosaic preparation。

当前视野按原生 VIEW_DEMAND/VIEW_WITHDRAWN 事件取集合，不用理论正方形代替。全部请求与最后仍需要的请求分别保留；未就绪数据按截尾区间参与 p50/p95，不只统计完成子集。这里 send-ready 只表示服务端可发送，不表示真实发包、玩家就绪或渲染。

每组累计 357 个原生视野需求、最后保留 289 个。B 最后视野三维度都在观察窗口内就绪；主世界全部请求中仍有 66 个未就绪、下界 14 个、末地零，因此不能把全部请求也说成已经完成。第 55 秒主世界当前视野就绪 276/289、下界和末地 289/289。末地两侧都完成有限轨迹的全部 525 FULL/437 send-ready，完成数上限相同，不证明最大吞吐相同；100.03% 仅来自实际窗口的毫秒级差异。

主世界中心目标从首次视野需求到 canonical 开始约 6.993 s；canonical 执行约 1.879 s，捕获/rehydrate 各约 1 ms，8.873 s 已准备好。此后等依赖到 22.364 s 才进入初始化光照，LIGHT 约 0.305 s、SPAWN 约 0.001 s、FULL 于 22.795 s、send-ready 于 22.854 s、ENTITY_TICKING 于 22.867 s。等待不能全部算成目标的 active compute，也不能把排队/依赖耗时误归为主线程文件系统阻塞。

主世界 B CPU 样本：FEATURES 31.31%、Noise/Surface/Biomes 30.22%、其它结构 21.00%、Stronghold/rings 2.66%。最常见叶方法包括 GradientNoise.permute、Climate.RTree.SubTree.search 与 Aquifer.computeSubstance；调用栈显示 FEATURES 的矿物/地牢读取会进入邻区高度/方块查询。分类有嵌套调用，不把 FEATURES 一栏全等同于装饰放块算法本身。

四 CPU 预算内，B 平均使用主世界 3.170 核、下界 1.033 核、末地 0.448 核；后两者前沿提前完成后长时间空闲，不作为持续满载能力。主线程仅占单核约 5.04%/3.89%/0.32%，未记录到卡服落后告警；这不是证明每个 tick 无延迟。GC 暂停累计约 1.526/0.547/0.230 s，主世界分配采样权重约 47.2 GB、峰值已用堆约 1.50 GB。它们值得继续观察，但没有证据把 GC 或主线程同步 stall 列为本组第一主因。

监视器等待是累计线程时间：主世界 GenerationContextRegistry.find/bind/unbind 合计约 0.968 s，下界 find 约 3.604 s，末地结构类型锁约 0.707 s；不能除以 60 秒直接当成 critical-path 占比，也不由本组结果批准新的锁优化。

首版归并器把实际窗口必须大于等于 60 秒作为条件，误拒绝 59.983 秒的 Vanilla。原生时钟在发出首个 JFR marker 之前开始，因此正式工具允许有界 marker 发出偏差，仍使用真实 59.978～60.015 秒归一化，不改写原始数据、不延长游戏。新的十项归并单测及全部 37 项性能工具测试通过；这次是分析工具边界修正，不是游戏失败。

## 结论

本 Target 主世界的主要差距是整片有限前沿的吞吐及依赖就绪，而不是只要优化中心 Chunk 的 1.879 秒就能消除 22.854 秒等待。下界和末地成本较低，但请求延迟仍分别明显高于 Vanilla。只完成单组基线，尚未做高视距短测、配对优化保留与该 Target 的性能停止审查。

下一步只能根据实际热点登记有界候选；部分 BIOMES 数据义务和局部查询等尚未单独证明的本版快路径，不能借用其它 Target 的通过。当前没有修改生成合同、调度器或生产优化，也不把本次比值当作五 Target/BOP 收口。
