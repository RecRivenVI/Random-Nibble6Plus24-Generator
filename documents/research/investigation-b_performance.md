# 按需 B 的首次端到端性能测量

调查日期：2026-10-14。结论：按需 B 减少完整邻区对象，但本次真实生产前沿明显慢于保留的单 writer Ordering 2 路径，需要后续优化授权；没有切换旧世界或生产默认。

## 问题

B 能否同时完成严格切断、精确按需读取与可接受的探索性能？完整 ProtoChunk 数量减少是否等于生成成本下降？

## 方法

三组分别使用 fresh 世界、同一 master seed 123456789、Overworld `(125,-37)`、四逻辑 CPU、亲和性 `0xF00`、BelowNormal、单个重负载 JVM、3 GiB 最大堆、8/8 与 60 秒固定 PLAYER ticket 前沿。第 15、30 秒各移动两个区块。全部结构开启，没有更改 scheduler 或并发规则。

CLI 跳过初始出生准备，断开连接的玩家对象只作为原版 DistanceManager 的 ticket 来源，没有客户端 packet 或渲染。计数严格使用 WORKLOAD_START 到 WORKLOAD_END 的窗口，退出后的迟到完成不计入吞吐。JFR 和逐区块时间线写入 ignored 固定结果；命令与通过条件见[性能验证](../../validations/performance-worldgen/validation.md)。

旧组是保留的 scheduler Ordering 2 生产路径，不是原 B 单模块微基准。此轮每组一次，数据是首次受控测量，不宣称已排除全部机器和 JIT 噪声。

## 发现

| 指标 | 按需 B | 保留 Ordering 2 | 普通原版 |
| --- | --- | --- | --- |
| canonical 目标/秒 | 4.12 | 12.15 | 不适用 |
| FULL 完成数 | 91 | 441 | 525 |
| send-ready 完成数 | 55 | 361 | 437 |
| 第 55 秒当前 17×17 视野就绪 | 12.5% | 100% | 100% |
| 初始中心 ENTITY_TICKING 就绪代理 | 38.50 秒 | 17.32 秒 | 3.68 秒 |
| 目标准备均值 / P90 | 1.20 / 3.23 秒 | 0.36 / 0.73 秒 | 不适用 |
| 峰值准备队列 / 活动会话 | 121 / 15 | 129 / 10 | 0 / 0 |
| Structure CPU 采样占比 | 38.83% | 18.76% | 5.77% |
| GC 暂停累计 | 1.81 秒 | 1.74 秒 | 0.30 秒 |
| 采样分配量估计 | 76.8 GiB | 39.7 GiB | 7.0 GiB |

send-ready 不是玩家已经看到区块；ENTITY_TICKING 代理不是首次玩家出生。分配量来自 JFR 加权采样，不是存活堆或精确累计。没有出现运行期 server lag 警告，不能将“没有警告”写成已测最大 lag 为零。

典型中心 `(125,-37)` 的首次物理请求至 send-ready 为 38.36 秒：等待准备开始约 4.78 秒，目标计算与 detached 交接约 1.03 秒，已准备目标继续等待真实物理依赖约 32.18 秒，随后 POI、光照、SPAWN、FULL 与 send-ready 约 0.37 秒。目标在第 6.58 秒已准备好，并不意味着邻区就绪。此例不是 packet 或实际渲染时延。

按需 B 的主要新成本集中于 `LocalTerrainColumns.column/Batch`：局部高度或方块读取会为所需邻区建立密度批次，并重新取得精确结构地形适配。`CompactStructureInputs.resolve → createStructures → JigsawPlacement` 因此反复进入命中后的原版结构构造。Structure 约 38.8%、FEATURES 约 28.7%、Noise/Surface/Biomes 约 12.9% 的独占 CPU 分类，不能把这些比例再与嵌套 inclusive 方法比例相加。

`StructureTemplateManager` 在紧凑输入构造中的 monitor wait 累计约 44.9 秒；这是多个线程重叠的等待总和，不是玩家额外等待 44.9 秒。既有模板锁归属没有修改，本次只测量、不进入 D2。大量 byte/float 数组和 Jigsaw 对象分配说明“轻量对象表示”仍可能重复昂贵计算；GC 约占窗口 3%，不足以独立解释吞吐差距。

profile 文件检查仍只有两个世界生命周期调用、累计约 0.27 毫秒；新 B marker 另在加载边界检查一次，不进入 Chunk 热路径。91 次 SPAWN 都命中携带的 palette，没有重建旧 biome 邻区；其输入准备累计约 3.3 毫秒。POI、SPAWN 不是这次的第一计算瓶颈。

## 结论

B 的切断和完整交接可继续用于新地图验收，但按需读取尚未达到性能目标。首先值得研究的是减少同一 S(C) 会话内结构投影和局部查询批次的重复准备；再评估密集读取何时采用已证明的精确整块回退更便宜。不能以假空气、近似高度或漏结构换速度。

本轮不实施这些优化，不动模板锁、其它结构算法、旧存档、A/C 或 D2。新地图的真实进入、飞行、光照、跨界交互及保存重进仍由使用者验收，12/12、16/16 和长期稳定吞吐尚未测完；首个里程碑不能仅凭此测量判完成。
